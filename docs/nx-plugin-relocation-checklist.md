# NX Plug-in Deployment Troubleshooting Checklist

> **This file is the deployment / relocation troubleshooting reference for `nx-auto-mcp`.**
> For install steps see `../README.md`; for build script details see `BUILD_SCRIPTS.md`.
> All paths in this document are relative to the **package root** (`nx-auto-mcp\`, i.e. where `setup.bat` lives):
> the plug-in directory is `<root>\plugin\`, and NX's actual load point is `<root>\plugin\startup\`.

## Scenario

When relocating the NX C# plug-in to a new directory (or upgrading in place), it is easy to miss a config change, causing NX to load a stale DLL.

## Single-DLL Rule (Verified 2026-09-05 — The Only Deployment Standard)

**NX loads the plug-in from exactly one location: `custom_dirs.dat` → `startup\managed_plugin.dll`.**
For this package, that is `<root>\plugin\startup\managed_plugin.dll`.

Startup syslog proof (`%TEMP%\<username>*.syslog`, 2026-09-05 11:17 startup):
```
ManagedLoader.Load: C:\...\nx-auto-mcp\plugin\startup\managed_plugin.dll
Loaded assembly: managed_plugin ... from C:\...\plugin\startup\managed_plugin.dll
DotNet author license is present.  Authentication passed for ...\plugin\startup\managed_plugin.dll
```
custom_dirs.dat content = `C:\...\nx-auto-mcp\plugin` (single line, points to the directory containing `startup/`; generated by `setup.bat`).

**All other locations are ignored by NX** (disproved old assumptions on 2026-09-05):
- `plugin/application/managed_plugin.dll` — not read (deployed a new DLL here + LOCALAPPDATA, code behavior unchanged → the real culprit was the stale copy in startup that was never replaced)
- `%LOCALAPPDATA%\Siemens\NX2412\startup\managed_plugin.dll` — not read (a third stray copy was hidden here, also ineffective)
- `%LOCALAPPDATA%\Siemens\NX2412\application\managed_plugin.dll` — not read
- Proof #2: all three locations were unlocked (no process lock), **only `plugin/startup/` was locked by NX** — whoever is locked is the load point

**Standard procedure**:
1. Compile → `SignDotNet.exe` sign (required; signing rewrites DLL bytes → md5 changing before/after is normal)
2. **Only overwrite `plugin/startup/managed_plugin.dll`**; delete / do not create copies in any other location (multiple copies = the common root cause of both dual-instance and stale-code issues — see the 2026-08-04 dual-instance section below).
   ⚠️ "Single point" means the **assembly** has one location; the plug-in also reads a **data file** `plugin/startup/rules/rules_config.json` (`deploy.bat` copies it automatically; for manual deployment don't forget — see "3. Files that must exist in startup/")
3. Fully exit NX then restart; to avoid interrupting your session, use the "rename swap" method below. When the DLL is locked, `cp` reports `Device or resource busy`; **after closing the window ugraf.exe may not have exited** (window-close suspend is common) → `taskkill /F /IM ugraf.exe /T` as fallback
4. Verify: `node scripts/check-plugin-status.js` (tool count / version change) or grep `ManagedLoader.Load` in this startup's syslog to confirm the path

### Deploy Without Closing NX: Rename Swap Method (Verified 2026-09-11)

**Corrected understanding**: this section originally stated "DLL locked → must close NX". In fact
**Windows allows renaming an occupied file** (only write/delete are blocked), and NX's handle
**follows the renamed file**. So you can:

```bash
cd <root>
mv plugin/startup/managed_plugin.dll plugin/startup/_prev_managed_plugin.dll.<date>  # locked but renamable
cp plugin/bin/managed_plugin.dll plugin/startup/managed_plugin.dll                   # new name has no handle → writable
```

**Effect**: NX still runs old code (handle on the renamed file), but **the deploy point is ready**;
you can restart NX at any time to pick up the new DLL — no need to interrupt an active NX session
(especially when unsaved parts are open).
**Cleanup**: after confirming the new DLL took effect, delete `_prev_managed_plugin.dll.*`
(it is **not** named `managed_plugin.dll`, so NX does not load it — no dual-instance; but keeping
it violates the "single point" discipline).

Tested on the same day: NX stayed open the entire time (9 parts open), `plugin/build.bat run` →
sign → overwrite `plugin/startup/` succeeded.
**Note**: being able to overwrite ≠ being able to take effect — taking effect still requires restarting NX (the plug-in has **no hot-reload**).

### Three Gotchas When Writing .bat Files (Verified 2026-09-11, hit twice in a row)

When editing `build.bat`, a **completely non-executable** file was produced. Three gotchas stacked, each independently fatal:

| Gotcha | Symptom | Avoidance |
|--------|---------|-----------|
| **`\b` interpreted as escape** | `plugin\build.bat` — the `\b` becomes **backspace 0x08**, path splits into `plugin`+0x08+`uild.bat`; reports `'ild.bat' is not recognized as an internal or external command` | Write with **quoted-heredoc** (`<<'EOF'`), not nested strings in `printf`/`node -e` (`\\b` collapses to `\b`). After writing, `cat -A` to verify; **`grep -c $'\x08'` must be 0** |
| **UTF-8 Chinese comments** | cmd.exe decodes .bat using **OEM(cp936)**; UTF-8 CJK bytes become garbled → breaks parsing | .bat comments should be **ASCII only** |
| **LF-only line endings** | cmd.exe counts tag offsets by CRLF → tags silently misalign (e.g. `echo` outputs only `ho`) | After writing, verify `CRLF=N / bare-LF=0` |

**In one sentence**: writing Windows paths inside `printf`/`node -e` = minefield; use `<<'EOF'` heredoc + `sed -i 's/\r*$/\r/'`.

This package's build scripts are now single-source: `plugin/build.bat` **only compiles** into `plugin\bin\`;
`plugin/deploy.bat` (called by `build.bat run`, `deploy-only` can skip compile) handles
**signing → single-point overwrite of `plugin/startup/`**.
Neither copies to application / LOCALAPPDATA / NXBIN.

> ⚠️ **Two scripts with mismatched output locations = deployment silently ships stale DLL (actually hit 2026-09-11)**:
> If you still have a second older build script, its output may land in `<root>\bin\`, while the deploy script reads
> `plugin\bin\`. **Two scripts disagreeing on "where is the output" → the stale DLL gets deployed**;
> the symptom is the "tool count unchanged → loaded DLL from old directory" row in the symptom table below
> (measured tool_count stuck at 151 instead of 154, the delta being exactly 3 new tools).
> **One-line check**: `tr -d '\000' < plugin/startup/managed_plugin.dll | grep -c <new-tool-name>`
> (.NET strings are stored in UTF-16 heap; **must `tr -d '\000'` first**, bare grep always 0 → misleading).
> Lesson: **don't trust "should be fixed already"; trust reading the file.**

## Pre-Deployment Checklist (Must execute item-by-item on every DLL update)

### 1. Environment Variables
```powershell
[System.Environment]::GetEnvironmentVariable('UGII_CUSTOM_DIRECTORY_FILE', 'User')
[System.Environment]::GetEnvironmentVariable('UGII_USER_DIR', 'User')
# Must be: <root>\custom_dirs.dat   and   <root>  respectively
```
(Both set by `setup.bat`; NX reads them **only at startup**, so NX must be restarted after changes.)

### 2. custom_dirs.dat
Content must point to the path containing the `startup/` subdirectory (for this package: `<root>\plugin`, single line, generated by `setup.bat`).
⚠️ Do not manually point it at another directory — changing the directory = changing the load point, easily creating a dual-instance with old copies.

### 3. Files That Must Exist in startup/
```
plugin/startup/
├── managed_plugin.dll            ← C# plug-in DLL (produced by build.bat, not in this repo)
├── nx_mcp_plugin.men             ← Main menu bar definition
├── nx_mcp_plugin_view_popup.men  ← View right-click popup menu
├── nx_mcp_plugin_hotkey.btn      ← Hotkey button definitions
└── rules/
    └── rules_config.json         ← Rule metadata (deploy.bat copies from plugin/rules/; not in this repo, build artifact)
```

⚠️ **Missing `.men` files are the most common cause of plug-in buttons being "not registered".**

⚠️ **Omitting `rules/rules_config.json` produces no error** — `RuleEngine` silently falls back to built-in rules
(`RegisterAllRules()`). Both rule sets currently have the same 15 rules with identical ids / severities / applicable intents
(only some rule description wording differs; check thresholds are hardcoded in C# and do not read JSON `params`),
so omitting the copy **does not change check results**; but from that point on the config file is inert —
editing the JSON has no effect. When debugging "config changes have no effect", check this first.

### 4. DLL Must Be Signed (NX2412 Hard Requirement)
```batch
"%NX_ROOT%\NXBIN\SignDotNet.exe" plugin\startup\managed_plugin.dll
:: NX_ROOT detected by plugin\nx-env.bat; default install is C:\Program Files\Siemens\NX2412\NXBIN\
```
NX refuses to load unsigned DLLs without a clear error message.

### 5. Clean Up Old DLLs
Delete old `managed_plugin.dll` from all locations:
```
%LOCALAPPDATA%\Siemens\NX2412\application\
%LOCALAPPDATA%\Siemens\NX2412\startup\
<root>/startup/
<root>/application/
<root>/bin/                  ← added 2026-09-10: running the build script from wrong cwd generates it here
<root>/plugin/application/
```
**Dual-instance conflict**: having DLLs in both `startup/` and `application/` causes NX to load twice.

**Use a full disk scan instead of manual checklist** (checklists miss things, scans don't):
```bash
# Replace <your-work-dir> with the directory where you keep nx-auto-mcp
find <your-work-dir> /c/Users/<you>/AppData/Local/Siemens/NX2412 \
     -name "managed_plugin.dll" 2>/dev/null
```
Expected: only 2 types remain: `plugin/bin/` (build artifact), `plugin/startup/` (**the only load point**).
Historical backup/archive directories that still contain old copies are also stray copies → delete them too.
**Any extra path = stray copy → delete.**
> ⚠️ 2026-09-10 lesson: the previous round claimed "cleanup complete" but actually **missed `<root>/bin/`** — because
> that item was not in the checklist, manual checking naturally could not find it. **Don't trust manual checks; trust scans.**

**cwd trap (hardened 2026-09-10)**: `build.bat`'s output path was once relative `bin\managed_plugin.dll`.
`pushd %~dp0` only protected the **compile** step; the `clean` branch executed before `pushd` →
running `build.bat clean` from the wrong directory deleted the wrong file. Now uses `%~dp0bin\...` (absolute).
**Conclusion: build/deploy scripts must always use absolute paths (`%~dp0`), never depend on the caller's cwd.**

> ⚠️ **2026-09-11 correction**: the "changed to absolute path" above **was only applied to one script at the time**;
> another script in the same project still used relative paths. The checklist-by-checklist approach
> **cannot detect** this divergence (the checklist only describes the script in your hand).
> Same lesson as the `bin/` issue: **don't trust "should be fixed already"; trust reading the file — re-read after editing.**

## C# Code Key Rules

### GetUnloadOption Must Return AtTermination (3)
```csharp
public static int GetUnloadOption(string arg) { return 3; }
// Returning 1 (Explicitly) causes callbacks to fail after DLL unload
```

### RegisterApplication() Is Required
```csharp
// ❌ AddMenuAction alone is not enough
mb.AddMenuAction("NX_MCP_START_SERVER", callback);

// ✅ Must register the application first
mb.RegisterApplication("NX_MCP_PLUGIN", initCb, enterCb, exitCb, true, true, true);
mb.AddMenuAction("NX_MCP_START_SERVER", callback);
```

### NX2412 API Compatibility: Types Available at Runtime but Missing from SDK
The following types do not exist in the NX2412 SDK reference DLLs but exist in NX runtime assemblies:
- `NXOpen.UI` / `NXOpen.UI.GetUI()` — requires reflection call
- `NXOpen.MenuBar.MenuBarManager` — requires reflection to obtain delegate type
- `NXOpen.MenuBar.MenuBarManager.ActionCallback` — same as above
- `NXOpen.SelectionSubscriber` — use `dynamic` instead
- `NXOpen.NXMessageBox` — use `dynamic` with numeric enum values

**Correct approach for GetUI()** (do not use `Type.GetType("NXOpen.UI, NXOpenUI")` — it throws):
```csharp
// ✅ Search loaded assemblies without assembly-qualified name
var uiType = Type.GetType("NXOpen.UI", false);
if (uiType == null) {
    foreach (var asm in AppDomain.CurrentDomain.GetAssemblies()) {
        uiType = asm.GetType("NXOpen.UI"); if (uiType != null) break;
    }
}
if (uiType != null) {
    dynamic ui = uiType.GetMethod("GetUI", BindingFlags.Public|BindingFlags.Static).Invoke(null, null);
}
```

## Symptom Troubleshooting

| Symptom | Likely Cause |
|---------|-------------|
| NX menu shows old version number | **Not hardcoded** — the menu/popup reads the real value (`ContextMenuHandler.OnShowStatus()` + `ManagedPlugin.ShowStatus()` both use `PluginVersion.Full`, single source `plugin/PluginInfo.cs`). Showing old number = **still running the old DLL**, usually the copy in `plugin/startup/` was not replaced (same as "log only shows old timestamps" row) |
| Button appears but click does nothing | `ACTIONS STANDARD` (does not trigger C# callback) |
| Button does not appear at all | `.men` file missing or syntax error |
| "Missing valid action" | `.btn` file lacks a valid ACTIONS entry |
| Menu does not appear at all | `UGII_CUSTOM_DIRECTORY_FILE` not set |
| NX crashed, cannot connect to 1977 | Port occupied by old process or NX not fully loaded |
| Tool count unchanged | Loaded DLL from old directory |
| **Plug-in has new tools but MCP cannot call them** | ⚠️ **Connection snapshot** (≠ previous row!) — the tool is in the plug-in (`nx-tcp-call.js --list` can list it), but the MCP client's tools/list is a **snapshot taken at connection time**; newly deployed tools do not appear automatically. See next section |
| `cp` reports `Device or resource busy` (or `deploy.bat` prints `[ERROR] Copy failed` then exit code 1) | DLL locked by NX process — **this is a loud failure**: command errors out + non-zero exit, never "thought it deployed but didn't". Use the "rename swap" method, or close NX first |
| TCP works but menu not registered | `NXOpen.UI.GetUI()` returned null, or .men file missing |
| Click produces blank error dialog | Python stub crash (.btn + .py file incompatibility) |
| DLL load failure with no message | DLL not signed with SignDotNet.exe, or NXSigningResource.res not embedded at compile time |
| Menu does not appear (rare) | custom_dirs.dat accidentally moved/deleted (UGII_CUSTOM_DIRECTORY_FILE invalidated) |
| Menu appears but buttons do nothing | `RegisterApplication` failed → `GetUI()` returns null (NX2412 reflection issue) |
| Log only shows old timestamps | DLL at deploy point `plugin/startup/` was not replaced (copying to other locations does not take effect) |
| csc compile CS1567 | NXSigningResource.res path wrong or format is ASCII (536B) |
| SignDotNet "not compiled with NX resource bundle" | DLL compiled without `/resource:NXSigningResource.res` |

> **Do not confuse "loud" and "silent" failures** (the most misused row in this table):
> **File locked = loud failure** — `copy` / `cp` errors out immediately with non-zero exit (see `Device or resource busy` row above);
> you cannot "think it copied when it didn't". So **silent symptoms like "changed source but behavior unchanged" are basically NOT caused by locks**; instead:
> ① **The DLL at the deploy point was not replaced** (copying to `plugin/bin/`, `application/`, `%LOCALAPPDATA%` all do not count);
> ② **Output landed in the wrong directory** (a second old build script → `<root>\bin\`, see "mismatched output locations" at the top);
> ③ **Copy succeeded but NX was not restarted** — the plug-in has **no hot-reload**; "can overwrite ≠ can take effect" (see "rename swap" section).
> Fixed investigation order: first `grep ManagedLoader.Load` in this startup's syslog to confirm the **load path**, then compare the mtime of the DLL at that path.

## MCP Tool List Is a "Connection Snapshot" (Verified 2026-09-10)

**Symptom**: DLL deployed + NX restarted + plug-in self-reports correct tool count, but calling
a new tool via MCP gives `No such tool available: nx_xxx`.

**Root cause** (**not a deployment problem — stop digging through DLLs**):
Both layers use snapshots —
- Plug-in side: `let pendingTools = loadTools();` in `mcp/nx-auto-mcp.js` is **module-level**,
  fetched once at process start and never refreshed; subsequent calls reuse the cached promise.
- Client side: MCP client fetches `tools/list` **once at connection time**.

So newly deployed tools on the NX side **do not automatically appear** in the client tool list.

**Diagnosis** (30 seconds to tell "bad deploy" from "stale snapshot"):
```bash
node scripts/nx-tcp-call.js --list    # plug-in's real list (is the new tool there?)
node scripts/nx-tcp-call.js --ping    # returns tool_count field, cross-check with --list
```
- New tool **is** in the list → **snapshot issue**: reconnect MCP (restart Claude Code session); for immediate use, use TCP direct below.
- New tool **is not** in the list → real deployment issue: go back to "Single-DLL Rule" + symptom table above.

**Workaround: TCP direct** (`scripts/nx-tcp-call.js`)
```bash
node scripts/nx-tcp-call.js <toolName> '{"k":"v"}'      # call tool (most common)
node scripts/nx-tcp-call.js --list                      # list all tools
node scripts/nx-tcp-call.js --ping                      # connectivity + tool_count
node scripts/nx-tcp-call.js --raw <method> '{"k":"v"}'  # call any plug-in method directly
```
Exit codes: `0`=success / `1`=tool failure / `2`=usage error — usable as script assertions.

**Plug-in TCP protocol notes** (captured 2026-09-10):
- Call tool = `{method:"tool", id:1, params:{tool:"nx_xxx", ...}}`
- List tools = `{method:"list_tools", id:1, params:{}}` ← **pass the method name directly**, not `method:"tool"`
  (previously caused: wrapping in `method:"tool"` gave "unknown tool: list_tools")
- Supported methods (match `plugin/TcpServer.cs` `RegisterMethod` calls exactly, 11 total):
  `ping, get_selection, get_model_summary, tool, list_tools,
  measure, list_features, modify_expression, export, undo, get_parameters`
  (`nx-tcp-call.js --methods` prints this table; the `execute` method in old docs was removed from the plug-in and is no longer registered)
- ⚠️ **Only `nx_open` gets special handling from the MCP server**: `mcp/nx-auto-mcp.js` intercepts it
  and uses `child_process.exec` to launch `ugraf.exe -nx` directly (no TCP). Calling it via this script is pointless —
  it hits a **different implementation** in the plug-in (`plugin/tools/UtilityTools.cs` `OpenNxTool`,
  uses PowerShell `Start-Process`), and when NX is already running it always returns `already_running`.
- ⚠️ **`nx_close` has no special handling**: MCP and this script use **the same TCP path**,
  both reaching the plug-in's `CloseNxTool`. No-argument call = `session.Parts.CloseAll()` + `session.Exit()`;
  if graceful close throws, falls back to `Process.Kill()`; passing `{"force":true}` kills the process directly.
  **It discards all unsaved changes and may forcefully kill the NX process** — do not treat it as "safe restart NX"

## Deployment Steps (Full Procedure — Single-Point Since 2026-09-05)

> ⚠️ **Use the package root as working directory throughout** (consistent with the convention at the top of this file).
> `cd` persists, and switching directories mid-procedure causes every subsequent relative path to
> **silently point to the wrong place**; the scripts below can be called from any cwd
> (`plugin\build.bat` internally uses `pushd %~dp0`), so **you do not need** `cd plugin`.

```batch
:: 0. Ensure you are at the package root (all paths in this file are relative to it)
cd /d <root>

:: 1. Compile (call scripts under plugin by path, no need to enter plugin directory)
plugin\build.bat
:: In PowerShell / Git Bash write .\plugin\build.bat
:: Or one-click: plugin\deploy.bat (auto compile→sign→copy to plugin\startup\: DLL + rules\); plugin\build.bat run is equivalent
:: ⚠️ build.bat with no arguments only compiles to plugin\bin\, does not deploy — setup.bat checks startup\, will judge "not built"

:: 2. Sign (NX2412 required; unsigned DLL silently rejected)
"%NX_ROOT%\NXBIN\SignDotNet.exe" plugin\bin\managed_plugin.dll

:: 3. Deploy — two targets: DLL + rule config (do NOT copy to other locations!)
copy /Y plugin\bin\managed_plugin.dll plugin\startup\managed_plugin.dll
if not exist plugin\startup\rules mkdir plugin\startup\rules
copy /Y plugin\rules\rules_config.json plugin\startup\rules\rules_config.json
:: ⚠️ Don't forget the second line: RuleEngine reads config from "own assembly location\rules\rules_config.json",
::    omitting = silent fallback to built-in rules (deploy.bat does both automatically; only manual deployment needs this)

:: 4. Ensure .men files are in startup/
dir plugin\startup\*.men

:: 5. Fully exit NX then restart (process may not exit after window close → taskkill fallback)
taskkill /F /IM ugraf.exe /T
start "" "%NX_ROOT%\NXBIN\ugraf.exe"

:: 6. Verify status (replaces manual menu check)
node scripts\check-plugin-status.js --watch
:: ── waits for plug-in to come online, then outputs: version, tool count, menu registration, GetUI, TCP ──
```

### Status Diagnostic Tool

`scripts/check-plugin-status.js` — one-click verification of plug-in deployment success:

```bash
node scripts/check-plugin-status.js           # full: NX process→TCP→version→menu→GetUI→logs
node scripts/check-plugin-status.js --online   # online status only
node scripts/check-plugin-status.js --log      # startup log only
node scripts/check-plugin-status.js --watch    # wait for plug-in to come online after deploy
```

Diagnostic output includes:
- Whether NX process is running
- Port 1977 connectivity
- Plug-in version + tool count
- **Menu registration success/failure reason**
- **Whether GetUI found NXOpen.UI**
- Recent startup logs

## 2026-07-23 Key Finding: 3 Fatal Deployment Traps

### Trap A: custom_dirs.dat Accidentally Removed = Menu Disappears

The `UGII_CUSTOM_DIRECTORY_FILE` environment variable points to `custom_dirs.dat` under the package root. **Any move/delete of this file** (e.g. backup, cleanup) causes:
- NX falls back to the default `custom_dirs.dat` (`C:\Program Files\Siemens\NX2412\UGII\menus\`)
- Plug-in menu disappears completely (TCP may still be running)
- No error reported — silent failure

**Symptom**: Menu shows "NX MCP Plugin" but content is blank + buttons unresponsive.
**Verify**: `grep CUSTOM_DIR "%TEMP%\<username>*.syslog"` to check the path NX actually loaded.
**Fix**: Re-run `setup.bat` to regenerate (it also re-sets both environment variables).

### Trap B: SignDotNet Signing Requires .res Embedded at Compile Time

SignDotNet only signs DLLs that had `NXSigningResource.res` embedded at compile time. Compile without embedding → signing passes falsely → NX silently rejects.
```batch
:: ✅ Complete flow
csc /resource:NXSigningResource.res ... /out:managed_plugin.dll
"%NX_ROOT%\NXBIN\SignDotNet.exe" managed_plugin.dll
:: NXSigningResource.res content: NXAUTHBLKNT<hundreds of spaces>NXAUTHBLKNT (ASCII 536B)
:: This package's build.bat reads from %NX_ROOT%\UGOPEN\NXSigningResource.res
```

### Trap C: startup/ DLL Takes Precedence Over application/

NX load order: `startup/managed_plugin.dll` > `application/managed_plugin.dll`.
When old and new DLLs are mixed across locations, the old DLL (startup/) overrides the new DLL (application/).
**Symptom**: Logs not updating, code changes ineffective (appears to run old code).

> 📌 Current rule (since 2026-09-05): `application/` is **not in the load path at all** (see Single-DLL Rule at top).
> This item is kept as historical reference — if you place a DLL in `application/`, you may hit "changes have no effect".

## Additional Common Pitfalls

### AddMenuAction Delegate GC Collection

After C# registers `AddMenuAction(name, delegate)`, if the delegate is a local variable (e.g. the return value of `DynamicMethod.CreateDelegate`), GC may collect it after registration. Symptom: log shows successful registration, but clicking the button produces no `[BTN]` log entry.

Solution: Store the delegate in a `static List<Delegate>` field.

### DLL Dual-Instance Loading (Verified 2026-08-04; merged into Single-DLL Rule section since 2026-09-05)

> This section's historical issue has been fully absorbed by the "Single-DLL Rule" at the top: multiple copies = root cause of dual-instance / stale code residue. As of 2026-09-05 all stray copies have been deleted (`plugin/application` + `%LOCALAPPDATA%` startup/application), leaving only `plugin/startup/managed_plugin.dll`. The text below is kept as historical and troubleshooting reference.

**Symptom**: Code changed 5 times, NX behavior unchanged — because NX loaded **two** DLLs, the older one loaded first and took effect.

When both `<root>/startup/` and `<root>/plugin/startup/` contain DLLs, NX loads two instances. `custom_dirs.dat` points to `plugin/`, but the package root itself may also land in NX's search path.

**Verify**: `grep "Loaded assembly" %TEMP%\<username>*.syslog` — if two paths appear = dual instance!

**Solution**:
```
rm startup/managed_plugin.dll             # misaligned copy at package root
rm application/managed_plugin.dll
rm plugin/application/managed_plugin.dll
# Keep only plugin/startup/managed_plugin.dll
```

**Warning**: Having DLLs in both `plugin/application/` and `plugin/startup/` is also dual instance!
